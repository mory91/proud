# Pull Request Overview

Review the description, changed files, commits, checks, and conversation in one Vim-native surface. The details pane keeps two columns of horizontal inner padding on both sides, so text, separators, and native cards begin and end away from the pane edges. Long titles, metadata, and description text use the shared `ui.content_lines` capability. Wrapped content fits the constrained content box, while non-wrapped content retains the complete padded line for native horizontal navigation instead of being truncated. The capability follows Neovim's global `wrap` setting unless explicitly overridden. Once a reusable credential is resolved, the complete two-pane workspace appears immediately with loading content, then replaces that content in place when GitHub API data arrives. Credential access validation continues in the background instead of delaying the scene. Reviewers, labels, the description, and conversation are populated from GitHub API data rather than display fixtures. Overview sections use muted-grey separator rows. Conversation entries use reusable native Neovim rounded floating windows: root cards blend into the overview background, replies receive only a subtle grey shade, and each card combines author, review or comment metadata, and relative age in its header before the message. Review summary bodies and inline review comments both render; when a review summary is empty, its linked review messages appear as threaded cards beneath the review. GitHub reply links render as narrower indented cards beneath their parent. The conversation ends with a comment box (design screen 2): `Comment · markdown · <C-s> post · <Esc> draft` with an accent border, showing the draft when there is one.

The conversation is explorable with the cursor. `]]` and `[[` step through the description first and then every card, the comment box last; moving inside a card keeps it focused, and the focused card gets an accent border. `r` replies to the item under the cursor and `c` (or `<CR>` on the comment box) writes a new PR comment. Both open a markdown editor in the conversation itself, in rows the layout keeps free: at the end for a comment, under the whole thread for a reply. The editor grows with its text, completes `@` mentions from the PR author and everyone in the conversation, posts with `<C-s>`, and keeps the draft with `<Esc>` (also when the overview closes). Replies follow GitHub: an inline review comment gets a threaded reply to its thread's first comment; the description, reviews and PR comments have no threads on GitHub, so `r` quotes them into a new PR comment, like GitHub's "Quote reply". A posted comment shows at once and the cursor lands on it; a failed post keeps the editor and the text and shows GitHub's message. Without a GitHub provider (the demo) comments stay local. The editor is the shared `proud.ui.composer`, also used by the thread window.

File viewed state is tracked independently so reviewers can resume work without rereading completed files. `<CR>` or `d` on a file opens the pull request's diff page (the compare page) on that file; `<CR>` on a commit opens it on that commit's change. `<leader>e` hides or shows the sidebar.

## Related Code

- `feature.lua` normalizes pull request details, tracks viewed files, and composes the overview.
- `features/conversation_cards/feature.lua` provides the reusable native card component used for the conversation section.
- `tests/unit_spec.lua` verifies symmetric overview padding for wrapped and non-wrapped content, file-state, grey separators, conversation metadata, nested replies, semantic colors, and fixed-width rendering across terminal sizes.
- `tests/e2e_spec.lua` verifies conversation navigation, focus, quote and threaded replies, comments, drafts, failed posts, the session's GitHub calls, the viewed-file keyboard workflow, overview-to-diff navigation, delayed provider hydration, native card rendering, and stale-safe placeholder rendering.
- `bench/benchmark.lua` covers 200 changed files and 250 description lines.
- `tests/memory_leak_spec.lua` verifies repeated real-screen open/close lifecycle remains within the feature's memory and resource SLA.

Checks distinguish success, failure, pending, skipped, and neutral with semantic icons and colors. Failures sort first, pending checks next; rows show duration or state, and Enter opens the available details URL. The header includes passing, failing, and pending counts.

Live overviews poll every 15 seconds while checks are pending. Polling pauses in other tabs, avoids overlapping requests, retains the last result on errors, and stops on completion or scene closure. Only the checks subtree is updated, preserving drafts, local viewed marks, and conversation content.
